1. Box Types: Concrete vs. Abstract vs. Interface

Slide 3 / 8
  • Standard Concrete Class ((C) green circle):
    • Where in diagram: Order, Customer, Restaurant, MenuItem, OrderLine, BikeCourier, CarCourier, StripeGateway, PayPalGateway, OrderService, DeliveryDispatcher.
    • Meaning: A fully implemented blueprint that can be instantiated directly using new (e.g., new Order(cust)).
  • Abstract Class ((A) blue circle + Italicized Name):
    • Where in diagram: User and Courier.
    • Meaning: Partial blueprint that cannot be instantiated directly (new Courier() is a compiler error). Shares common state (#userId, #currentLat) and common behavior (+updateLocation()) among subclasses.
    • Abstract Methods (Italicized): Inside Courier, look at +calculateETA(distanceKm: double): int. Written in italics = no method body (abstract int calculateETA(double d);). Concrete children (BikeCourier, CarCourier) must override and implement it.
  • Interface ((I) purple circle + <<interface>> stereotype):
    • Where in diagram: <<interface>> PaymentGateway.
    • Meaning: A pure contract of capabilities ("Can-Do") with no state (no instance fields). Only declares method signatures (+charge(), +refund()). Implementing classes promise to provide the code.

2. Inside the Box: Compartments, Visibility & Static

Slide 4 / 8

The 3 Compartments & Type Syntax

  • Top: Class Name
  • Middle: Attributes (Fields / State). Empty in OrderService & DeliveryDispatcher because they only have associations!
  • Bottom: Operations (Methods & Constructors).
  • Reversed Type Syntax (Name : Type):
    • Field: [vis] name : Type [= default]
      → - orderCounter: int = 0
    • Method: [vis] name(arg: Type): ReturnType
      → + charge(amount: double): boolean

Access Modifiers & Typography

  • - (private): Visible only inside this class (e.g., -apiKey: String in StripeGateway, -orderId: String in Order).
  • # (protected): Visible to this class and subclasses (extends). Look at User (#userId, #name) and Courier (#currentLat, #isAvailable) so children can access them directly!
  • + (public): Visible to everyone (+placeOrder()).
  • Underlined = static (Class-level):
    In Order: -orderCounter: int = 0 and +getOrderCount(): int are shared across the entire class in RAM, not per instance.

• BikeCourier ──▷ Courier
• CarCourier ──▷ Courier 		"B is a type of A." Arrow always points UP to the parent. BikeCourier inherits all fields and methods of Courier AND User (2-level hierarchy).

• PayPalGateway ╌╌▷ PaymentGateway 		"B fulfills contract A." Dashed line means the parent is purely a specification (interface); the child realizes (makes real) those abstract methods.

Quick Visual Rule:

  • Both Inheritance and Realization end with a closed hollow triangle (▷) pointing to the abstraction.
  • Solid line = extending a class (extends). Dashed line = implementing an interface (implements).

Line Style UML Name Exact Java Equivalent Where in Diagram What to Tell Students
4. Empty Diamond + Solid Line
◇──>		 Aggregation (הכלה חלשה / שייכות) private List<B> itsBs;
where B is created outside and passed in (e.g., registerCourier(c)).		 • Restaurant "1" ◇──> "*" MenuItem (itsMenuItems)
• DeliveryDispatcher "1" ◇──> "*" Courier (itsFleet) 		"Whole-Part container WITHOUT lifecycle death." DeliveryDispatcher manages a fleet of Couriers. If we destroy DeliveryDispatcher, the Courier objects still survive!
5. Solid Black Diamond + Solid Line
◆──>		 Composition (הכלה חזקה / בעלות מלאה) private List<B> itsBs;
where B is instantiated inside A (new OrderLine(...)) and never shared.		 • Order "1" ◆──> "1..*" OrderLine (itsOrderLines) "Strict Whole-Part WITH lifecycle death." Order.addLine(item, qty) internally creates an OrderLine. Exclusive to 1 Order. If Order is deleted, all its OrderLines die with it.

Crucial Diamond Placement Rule:

  • The diamond (empty ◇ or solid ◆) ALWAYS touches the Whole / Owner / Container (Restaurant, DeliveryDispatcher, Order), and the arrow points to the Part (MenuItem, Courier, OrderLine).

4. Reading Multiplicity & Key Design Questions

Slide 8 / 8

Rule: "Stand on Class A, look across the bridge to Class B, and read the number next to B."

  • Order "*" ──> "1" Customer (itsCustomer):
    • Stand on Order, look at Customer → 1: "Every Order belongs to exactly 1 Customer (in field itsCustomer)."
    • Stand on Customer, look back at Order → *: "A single Customer can place 0 to many (*) Orders over time." (Default if unwritten = 1).
  • Order "1" ◆──> "1..*" OrderLine (itsOrderLines):
    • An Order must contain at least 1 (1..*) OrderLines (no empty orders!). Every OrderLine belongs to exactly 1 parent Order.
  • Courier "0..1" <──> "0..1" Order:
    • Why 0..1 instead of 1? When an Order is first created/cooking, it has 0 couriers assigned; once dispatched, it has 1. An idle Courier has 0 orders; while delivering, they have 1.
  • Why does OrderLine exist instead of connecting Order directly to MenuItem?
    • OrderLine stores quantity and unitPriceSnapshot at the moment of purchase so future menu price changes don't corrupt past orders!
