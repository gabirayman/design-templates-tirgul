From Interaction Between Objects (Sequence) to the Behavior Inside One Object (Statechart)

  • What is a Statechart?
    • Models how one object reacts to events over its lifetime, depending on the state (מצב) it is currently in.
    • The same event can do different things in different states — that is the whole point.
  • Reactive Classes (Lec02, Slide 23):
    • Only classes with a real lifecycle get a statechart. In BiteExpress: Order and Courier.
    • Customer, MenuItem, OrderService, DeliveryDispatcher just hold data or call methods — no statechart.
  • The Bridge from Part 2:
    • The events we GENerated in the sequence diagrams (evPaid, evAssignOrder, ...) land in an object's event queue. The statechart defines what happens next.

Bad Design First: The Boolean-Flags Order

Slide 2 / 8 
class Order {
    boolean paid, preparing, outForDelivery, delivered, cancelled;

    void cancel() {
        if (!delivered && !cancelled) {
            if (paid && !preparing) refund();
            else if (preparing && !outForDelivery && withinGracePeriod()) refund();
            cancelled = true;   // paid is still true, preparing may still be true...
        }
    }
}

What is wrong?

  • 5 booleans = 32 combinations, but the order has only 6 legal situations.
  • Nothing prevents delivered && cancelled or paid && cancelled.
  • Every new feature adds another if to every method.

The fix

  • The order is in exactly one state at a time: Created, Paid, Preparing, OutForDelivery, Delivered or Cancelled.
  • Each state lists which events it reacts to — everything else is ignored.

2. Same Event, Different Behavior: evCancel

Slide 5 / 8
Current State Transition What Happens
Created evCancel → Cancelled Nothing was charged yet, so there is nothing to refund.
Paid evCancel / refund() → Cancelled Money was charged and the kitchen has not started: refund and cancel.
Preparing evCancel [withinGracePeriod] / refund() → Cancelled Guard: only if withinGracePeriod is true. If the guard is false, nothing happens and the order stays in Preparing.
OutForDelivery (no evCancel transition) The event is ignored. This is a design decision: cancellation is not allowed once the courier left.
Compare with the bad design: the boolean version needed one nested if to get this right. Here the answer is visible by reading the arrows — and a missing arrow is a deliberate rule, not a forgotten case.

3. The Courier Statechart: Objects Talking via Events

Slide 6 / 8

Reading the Chart:

  • Event with parameters: evAssignOrder carries the order. The action itsCurrentOrder = params.order stores it (role name itsCurrentOrder from our class diagram).
  • Sending an event to another object: itsCurrentOrder.GEN(evPickedUp) and itsCurrentOrder.GEN(evDelivered) fire into the Order's queue — these are exactly the events the Order chart waits for.
  • Querying a state: isAvailable() { return IS_IN(Available); } — this is how :DeliveryDispatcher decides in findAvailableCourier().
  • evPickup / evDropOff come from outside (the courier pressing a button in the app).

4. Closing the Loop: Sequence Diagrams ↔ Statecharts

Slide 7 / 8
Event Sent By → Handled By Where It Is Sent Transition
evPaid :OrderService → order Seq. 1, branch [isPaid] Created → Paid
evPaymentFailed :OrderService → order Seq. 1, branch [payment failed] Created → Created / showError()
evPrepareOrder :OrderService → rest Seq. 2 Restaurant replies with evAccept to the order
evAccept rest → order Restaurant's reaction Paid → Preparing
evAssignOrder :OrderService → courier Seq. 2, guard [courier != null] Available → ToRestaurant
evPickedUp courier → order Courier chart, evPickup Preparing → OutForDelivery
evDelivered courier → order Courier chart, evDropOff OutForDelivery → Delivered
Rule: every event that is sent in a sequence diagram must be received by a transition in some statechart — otherwise it goes nowhere. (The Restaurant reacts to evPrepareOrder too, but it has only two states, so we do not draw it here.)

5. Checklist for Your Own System

Slide 8 / 8

Choosing What to Draw

  • Draw a statechart only for the class with a real lifecycle — not one per class.
  • Be ready to explain why that class is reactive.
  • Find its lifecycle first: list the states, then ask "which event moves it from here to there?"

Checking Your Chart

  • Exactly one default transition into the first state.
  • Every transition reads Trigger [Guard] / Action (guard and action are optional).
  • At least one guard and one case of the same event in different states.
  • Every event name matches an event sent in your sequence diagram.
The Golden Rule across all three diagrams: Class diagram → method and role names. Sequence diagram → uses only those names and sends events. Statechart → handles those events. If a name appears in one diagram but not where it should in another, one of them is wrong.
