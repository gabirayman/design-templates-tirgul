From Static Structure (Lec01) to Dynamic Behavior (Lec02)

  • What is an Interaction / Sequence Diagram?
    • Models the runtime behavior of our system during a specific scenario (Use Case) — e.g., "Customer places and pays for an order."
    • Emphasizes the chronological order of messages passed between objects over time.
  • The Two Axes (Slide 9):
    • X-Axis (Horizontal): The participating Objects (Instances) in RAM.
    • Y-Axis (Vertical, Top → Bottom): Time. Moving down the diagram means moving forward in time.
  • Why split into two diagrams? (Slide 21 Rule):
    • Sequence diagrams are meant for clear, readable control flow. For complex scenarios, we split the flow into focused diagrams: 1. Place and Pay and 2. Dispatch Courier.

1. Object Naming, Lifelines & Activation Boxes

Slide 4 / 8

Object Naming Syntax (Slide 10)

  • Syntax: [instanceName]:[ClassName]
  • Why is the text underlined?
    In UML, an underline on a box header means this is a runtime Object (instance), whereas no underline (in Class Diagrams) means a Class type!
  • Named Instances: cust:Customer, rest:Restaurant, order:Order, gw:PaymentGateway, courier:Courier.
    Used when we reference a specific variable or parameter name.
  • Unnamed Instances (:[ClassName]): :OrderService, :DeliveryDispatcher.
    Rule: We omit the instance name when there is only one single instance of that class in the diagram!

Lifelines vs. Activation Boxes (Slides 9–10)

  • Life Line (הקו המקווקו האנכי):
    The dashed vertical line hanging below each object box. Represents the object's existence in memory during the scenario.
  • Activation Box (תיבת הפעלה — המלבן הצר):
    The narrow vertical white rectangle on top of the lifeline. Shows the exact time duration when the object is actively executing a method (or waiting on the call stack for a synchronous call to finish).
  • Notice on rest:Restaurant and order:Order:
    Synchronous calls (checkOpen(), addLine()) trigger an activation box; asynchronous events (GEN(...)) simply land on the lifeline (queued)!

3. Dynamic Object Creation (<<create>>) & Destruction

Slide 6 / 8

Why is the order:Order box floating in the middle of Diagram 1 instead of at the top?

  • Pre-existing Objects (Top Row):
    • cust:Customer, :OrderService, rest:Restaurant, and gw:PaymentGateway already exist in RAM before placeOrder() is called, so their boxes sit at the very top of the Y-axis (Time = 0).
  • Mid-Flow Instantiation (<<create>> Order(cust) — Slide 15):
    • order:Order does not exist when the scenario starts!
    • Only after checkOpen() returns true (inside the [isOpen] branch) does :OrderService call the constructor <<create>> Order(cust).
    • Therefore, the arrow points directly into the side of the order:Order box, and its lifeline begins at that exact moment in time!
  • Object Destruction (<<destroy>> — Slide 15 Note):
    • An object can delete another object via a <<destroy>> message (ending its lifeline with a big X).
    • Best Practice (Slide 15): Avoid modeling object destruction unless manual memory management (e.g., C++ delete without GC) is a critical requirement. Instead, in Java we send GEN(evPaymentFailed) so Order transitions to a cancelled/terminated state!

5. The Golden Exam Rule: Class Diagram ↔ Sequence Diagram

Slide 8 / 8

How to verify your Sequence Diagram against your Class Diagram (Slide 5 & 11):

  • Rule 1 — Method Ownership (Slide 5):
    If Lifeline A sends message foo() to Lifeline B (A → B : foo()), then the method +foo() MUST exist inside Class B (not Class A!).
    • service → rest : checkOpen() ⇒ checkOpen() is a method inside Restaurant.
    • service → order : addLine(item, 1) ⇒ addLine() is a method inside Order.
    • service → gw : charge(total) ⇒ charge() is a method inside PaymentGateway.
  • Rule 2 — Relationship / Dependency (Slide 11):
    Sending a message from A to B requires a link between A and B in the Class Diagram!
    • How can :OrderService call rest, gw, and order? Because they were passed as parameters / created locally (Dependency ..> in our Class Diagram!).
    • How can :OrderService call :DeliveryDispatcher in Diagram 2? Because OrderService has a Directed Association (──> itsDispatcher) to DeliveryDispatcher!
