S · Single Responsibility

Single Responsibility Principle

A class should have only one reason to change.
  • Each class owns one part of the system's functionality.
  • The question to ask: who or what could force me to edit this class?
  • More than one answer → more than one responsibility.

S · Auditing our design

Why User would keep changing

Each of these edits User:

  • A new password-hashing algorithm
  • Login with Google or an SMS code
  • Two-factor authentication
  • Locking the account after failed attempts

User is the parent of Customer and Courier — every security change ripples into both.

S · Auditing our design

Separate identity from authentication

public abstract class User {
    protected String userId, name, phone;
    public String getUserId() { return userId; }
    public String getName()   { return name; }
}

public class AuthService {    private Map<String, String> passwordHashes;     public boolean login(User user, String pw) {        String stored =            passwordHashes.get(user.getUserId());        return stored != null            && stored.equals(hash(pw));    }}

Login changes now touch AuthService only. User, Customer and Courier stay untouched.

A judgment call: Courier.calculateETA()

The Courier calculates its ETA itself?

For
  • The courier knows its own vehicle and speed
  • Bikes and cars genuinely compute ETA differently
Against
  • Real ETA also depends on traffic

O · Open / Closed

Open / Closed Principle

Open for extension, closed for modification.
Open

We can add new behavior to the system.

Closed

…without editing code that already works.

The key is abstraction: new behavior arrives as a new class behind an interface.

Depending on an abstraction

Only added 
class OrderService {
    Order placeOrder(..., PaymentGateway gw) {
        gw.charge(total);   // any gateway
    }
}

class ApplePayGateway implements PaymentGateway {    public boolean charge(double amount) { ... }    public boolean refund(String id)     { ... }}

A new payment method is one new class. OrderService never changes.

O · New requirement: drone delivery

Type checks everywhere

// DeliveryDispatcher
for (Courier c : itsFleet) {
    double d = distance(c, rest);
    int eta;
    if (c instanceof BikeCourier)        eta = (int)(d / 15 * 60);    else if (c instanceof CarCourier)        eta = (int)(d / 30 * 60) + 5;    if (eta < bestEta) { best = c; bestEta = eta; }
}

// EtaDisplay — the same chain, copied
if (c instanceof BikeCourier) ...else if (c instanceof CarCourier) ...

To add drones, we must edit:

  • DeliveryDispatcher — a new else if
  • EtaDisplay — the same else if again
  • …and every other copy of this chain

Miss one, and the app breaks on drones.

O · New requirement: drone delivery

Let each courier answer for itself

// DeliveryDispatcher — unchanged forever
for (Courier c : itsFleet) {
    int eta = c.calculateETA(distance(c, rest));
    if (eta < bestEta) { best = c; bestEta = eta; }
}

class DroneCourier extends Courier {    public int calculateETA(double km) {        return (int)km + 2;   // + takeoff    }}

The instanceof chain became one polymorphic call. Drones are one new class.

O · Open / Closed

Closed against what?

static void giveBikeBonus(Courier[] fleet) {
    for (Courier c : fleet)
        if (c instanceof BikeCourier)
            c.addBonus(10);
}
“Add drone couriers”

No edit needed — closed against this change.

“Cars get the bonus too”

Must edit the method — not closed against this one.

No design is closed against every change. We choose which changes to protect against.
