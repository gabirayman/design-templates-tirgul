L · Liskov Substitution

The principle

Code that works with a parent must keep working with any child — without knowing which child it got.
Not enough

"In real life, X is a kind of Y."
Same method names.

What counts

The child keeps every promise the parent makes.

L · Liskov Substitution

The "fake" test

Parent p = new Child();   // I promised you a Parent
useAsParent(p);           // call any Parent methods you like
You can tell

It behaves differently from what a Parent promises → it's a fake.

You can't tell

No test can catch it → it's a real subtype.

Part 1 · The fix

Is-a for the role, has-a for the person

public abstract class Courier {     // no "extends User"    protected double currentLat, currentLon;
    protected boolean isAvailable;
    /** reaches whoever is responsible */
    public abstract String getContact();
    public abstract int calculateETA(double km);
}

public abstract class HumanCourier extends Courier {
    private Driver itsDriver;      // has-a    public String getContact() {
        return itsDriver.getPhone();
    }
}

public class DroneCourier extends Courier {
    public String getContact() {
        return OPS_CENTER_PHONE;
    }
}
authService.login(drone, pw);

Compile error: DroneCourier is not a User.
The bug is caught before the app runs.

getContact() is a promise every courier can keep: the driver's phone, or the drone's operations center.

Part 1 · The fix

What we gained

Compile time

A drone can't reach AuthService or the promo list. Errors move from runtime to compile time.

Dispatcher unchanged

DeliveryDispatcher still works with Courier. Not one line edited.

No instanceof

"Contact your courier" calls getContact() on any courier — no type checks.

Why not extends Courier, User? Java allows one parent class — and a bike courier never really was a person. It has one.

Part 2 · Contracts

Every method is a contract

Precondition

What must be true before the call.

Caller's responsibility

What the method guarantees after it runs.

Method's responsibility
Invariant

Java has no require / ensure keywords — we write the contract as a comment. It's a promise, not syntax.

Part 2 · The bike problem

The fix: put the limit in the contract

Courier 
abstract class Courier {
    public abstract boolean        canDeliver(double distanceKm);
    /**
     * pre:  canDeliver(distanceKm)
     * post: result >= 0, within ±5 min
     */
    public abstract int calculateETA(
            double distanceKm);
}
DeliveryDispatcher 
for (Courier c : itsFleet) {
    double d = distance(c, rest);
    if (!c.canDeliver(d)) continue;    int eta = c.calculateETA(d);
    if (eta < bestEta) {
        best = c; bestEta = eta;
    }
}

Ask, don't assume. Still no instanceof — OCP stays intact.

Part 2 · The bike problem

Every courier, one contract

Bike
boolean canDeliver(double km) {
    return km <= 8;
}
Car
boolean canDeliver(double km) {
    return km <= 30;
}
Drone
boolean canDeliver(double km) {
    return km <= 10
        && batteryPercent > 20
        && weather.isFlyable();
}

The drone's real limits — battery, weather — are now visible to the dispatcher, not hidden exceptions waiting to crash it.

Part 2 · The bike problem
LSP doesn't forbid subclasses from having limits.
It forbids hidden limits.

If the client can't know about a limit, the client can't respect it.

Summary

The same bug, twice

The drone

Couldn't keep User's promise:
"I have a phone and a password."

The bike

Couldn't keep Courier's promise:
"Any distance up to 15 km."

The fix both times: change the hierarchy or the contract so that every promise in the parent is one all children can keep.
